# 架构与出口保护

使用与部署命令见 [README](../README.md)，运维和恢复步骤见[操作说明](operations.md)。

## 请求路径

客户端应用 → Squid HTTP 代理 → 代理 UID 的策略路由和 nftables 规则 → 已连接的 VPN 接口 → 目标服务。

HTTP 请求由 Squid 转发；HTTPS 通过 CONNECT 建立到目标 443 端口的隧道，客户端与目标进行 TLS 握手，代理不解密 TLS。`https_proxy` 使用 `http://`，表示客户端连接 HTTP 代理。

客户端安装器设置代理环境并清除旧的 `all_proxy`，不会修改客户端默认路由。Windows 的 `-SystemProxy` 还配置当前用户的 WinINet 代理；应用是否遵循这些设置取决于应用本身。

## 访问与 DNS

[Squid 配置](../templates/squid.conf.in) 按来源 CIDR 授权；另有回环健康监听。目标端口限于 80/443，CONNECT 仅允许 443，配置列出的私网、回环、链路本地等目标会被拒绝。

Squid 直接查询 `dns_nameservers` 指定的 IPv4 DNS 服务器，查询由代理 UID 发出并受出口规则约束。配置应避免使用主机的本地 DNS stub，因为 stub 转发的上游请求属于另一个进程用户。

## 两层出口限制

[firewall.sh](../scripts/firewall.sh) 管理专用 nftables 表 `inet rk_vpn_proxy`，仅限制 `rk-vpn-proxy` 用户的出站流量，依次允许：

1. 从代理监听端口返回客户端的连接回复。
2. 回环接口上的 Squid UDP helper 通信。
3. 经 `vpn_interface` 发出的流量，包括 DNS。

其余出站流量被拒绝。规则只控制代理用户，主机其他应用不受本项目规则直接限制。

另一层通过 `ip rule` 将代理 UID 的路由查找指向专用表（默认 240），表中镜像 VPN 默认路由，并设置 `unreachable` 兜底。每个 `allowed_clients` 网段有更高优先级的 main 表例外，用于客户端回程。资源预检查拒绝专用表或规则被外部程序占用的已识别冲突。

路由所有权按完整签名判断：VPN 默认路由必须引用配置的 `vpn_interface`，其他设备上同样写着 `metric 100` 的默认路由属于其他服务，预检查会拒绝、清理会保留。首次安装时若表中已存在签名相同的路由而没有部署记录（`/var/lib/rk-vpn-proxy-deploy/deployed`，由安装成功后写入），同样拒绝占用，避免把外部服务的路由当成自己的残留。

预检查与守护检查的最后一步是内核真实路由验证：对探测地址 `8.8.8.8`、`2606:4700:4700::1111` 执行 `ip route get <地址> uid <代理UID>`，要求回答经 VPN 接口或不可达。优先级更高的外部规则（例如 `50: from all lookup main`）会抢先完成路由查找、使本项目规则失效，只有这一步能发现该状态；若回答经其他接口即判定第二层失效。这两个探测地址不得加入 `allowed_clients`，配置校验会直接拒绝。

规则优先级从候选值 90 开始分配，跳过已有优先级，并检查客户端规则先于本项目兜底规则。此分配不保证优先于所有其他服务；管理员仍需检查已有策略路由、保留本项目资源，并保证客户端经 main 表可达。公网客户端白名单也会形成 main 表例外，评估出口边界时须考虑这些目的网段。

IPv6 同样具有代理 UID 规则和不可达兜底；VPN 接口具备 IPv6 默认路由时会尝试镜像该路由。服务端监听和配置流程目前仍按 IPv4 实现。

## 守护与故障边界

防火墙单元在两层规则安装并检查通过后通知 systemd 就绪，代理依赖该单元；代理启动前再次执行 `--check`。守护循环每次睡眠 1 秒后核对完整 nftables 规则（忽略计数值），修复并检查策略路由，最后验证代理 UID 的内核实际路由（探测地址经 VPN 或不可达）。

- nftables 表缺失或被修改时，守护进程失败退出，systemd 通过 `BindsTo` 联动停止代理；部署单元同时显式停止代理。
- 策略路由失效（规则缺失、顺序错误或实际路由被外部规则抢先）时清除健康标记，并在部署单元（`RK_VPN_MANAGE_PROXY=1`）下停止代理，直到修复后重新验证通过才恢复启动；VPN 掉线但有不可达兜底不属于失效，代理保持运行等待恢复。
- 仅删除 nftables 表时，专用策略路由仍为非客户端目的流量提供 VPN 或不可达路由。
- VPN 接口消失时保留不可达兜底；接口和默认路由恢复后，守护进程尝试重新镜像 VPN 路由。

循环检查、命令执行和 systemd 停服存在调度延迟，不承诺固定的 1 秒恢复时间。外部策略路由或同时修改两层保护的特权操作可能改变保护效果；隔离测试的零泄漏门禁只验证其指定故障与流量。

停止服务保留规则。修复后可重新启动防火墙和代理；清理或恢复应使用项目回滚流程，避免运行中手工撤去保护。

## 健康状态与运行文件

定时器开机约 45 秒后首次触发，此后约每 60 秒运行健康检查。检查以 `rk-vpn-health` 用户执行，记录：

| 状态 | 含义 |
| --- | --- |
| `VPN_UP` | VPN 接口有 IPv4 地址 |
| `VPN_ROUTE_OK` | DNS 目标按代理 UID 查询的路由指向 VPN |
| `FIREWALL_ENFORCED` | 守护进程最近 3 秒内刷新了保护检查标记 |
| `PROXY_REACHABLE` | 回环代理成功访问出口 IP 查询服务并返回可接受格式 |

状态保存在 `/var/lib/rk-vpn-proxy/status`，出口 IP 保存在同目录 `exit-ip`；状态和出口 IP 变化写入 journal。探测依赖外部服务，失败需结合日志判断，不直接等同于代理整体不可用。健康检查不负责 VPN 重连，也不发送外部告警。

配置位于 `/etc/rk-vpn-proxy/`，下载程序与生成的客户端安装器位于 `/usr/local/lib/rk-vpn-proxy/`，日志位于 `/var/log/rk-vpn-proxy/`。Squid 禁用磁盘缓存，日志按部署配置每日轮转、保留 7 份。
